# 桌面应用发布

## 发布矩阵

| 平台 | 架构 | 安装包 | 构建环境 |
| --- | --- | --- | --- |
| macOS | arm64 | DMG、ZIP | macOS Apple Silicon |
| Windows | x64 | NSIS、ZIP | Windows runner |

当前产物默认未签名、未公证。正式公开发布前需要分别配置 Apple Developer 与 Windows 代码签名凭据。

## 本地构建

根目录执行：

```bash
npm ci
npm --prefix frontend ci
uv sync --directory backend --frozen
uv pip install --python backend/.venv/bin/python 'pyinstaller<7'
npm run dist:mac
```

Windows 原生环境执行：

```powershell
npm ci
npm --prefix frontend ci
uv sync --directory backend --frozen
uv pip install --python backend/.venv/Scripts/python.exe 'pyinstaller<7'
npm run dist:win
```

产物位于 `release/`。构建过程包含：

1. 构建 Vue 前端；
2. 编译 Electron 主进程；
3. 用当前平台的 Python 3.12 + PyInstaller 生成 `backend-runtime`；
4. 用 electron-builder 生成安装包。

## 统一数据目录

开发模式和打包模式统一使用系统用户数据目录，不再把运行数据写入项目目录或应用包：

- macOS：`~/Library/Application Support/工具盒子`；
- Windows：`%APPDATA%/工具盒子`；
- Linux：`~/.config/工具盒子`。

临时任务、上传文件、SQLite 数据库和 MinerU 模型缓存都以该目录为根。Electron 开发启动器和生产主进程都会向后端注入 `TOOLBOX_DATA_DIR`，直接运行后端时也使用同一默认目录。

旧开发数据已直接迁移到统一目录；源码启动不会执行自动迁移。后续开发和打包只使用统一用户数据目录，项目内旧目录不再作为运行时数据目录。

## 后端运行时

安装包内置 PyInstaller 后端，不要求用户额外安装 Python 或 uv。打包后应用包内资源保持只读，所有运行时数据写入上述用户数据目录。MinerU 的 pipeline 模型默认不随安装包携带，首次使用深度解析时按需写入用户数据目录。

`backend/resources/` 被 Git 忽略：

- 构建机存在证件照模型时，会随后端运行时打入安装包；
- 没有模型时，证件照功能会在工具列表中显示不可用；
- 未提供便携版 LibreOffice 时，Word 转 PDF 依赖目标机器已有的 LibreOffice。

### MinerU 模型与首次深度解析

- 安装包包含 MinerU 运行代码，但默认不包含 pipeline 模型权重；模型缓存位于统一用户数据目录下的 `resources/mineru`，可通过 `MINERU_MODEL_PATH` 指定其他位置。
- 深度解析首次运行或检测到缓存不完整时，后端通过打包运行时的 `--toolbox-mineru-models` 入口执行模型下载，并从 ModelScope 获取 pipeline 模型；开发环境对应的下载命令为 `mineru-models-download -s modelscope -m pipeline`，下载完成后后续任务复用本地缓存。
- 模型下载与 PDF 转换使用独立超时：`MINERU_MODEL_DOWNLOAD_TIMEOUT` 默认 1800 秒，`MINERU_CONVERT_TIMEOUT` 默认 600 秒。两项均可通过环境变量覆盖。
- 模型下载需要网络连接、可写的用户数据目录和足够磁盘空间；模型准备失败不会影响标准 PDF 解析、EPUB、图片和二维码工具。
- 打包验收必须覆盖：无模型缓存的首次深度解析、下载中断后的再次启动、已有缓存的快速解析，以及 frozen 后端执行模型下载入口的场景。

## 自动更新

更新源为 GitHub Releases（`ddll8023/tools`）。每次发布必须递增根目录 `package.json` 的版本并创建 `v*` 标签。Release 必须保留以下文件：

- macOS：DMG、ZIP、`latest-mac.yml`、blockmap；
- Windows：NSIS、ZIP、`latest.yml`、blockmap。

### macOS（免签名自定义更新器）

当前产物未配置 Apple Developer ID 证书，而 Squirrel.Mac/electron-updater 会在“重启安装”阶段校验 `.app` 代码签名，未签名产物会报 `Code signature at ... did not pass validation`。因此 macOS 走独立更新链路（`electron/mac-updater.ts` + `electron/update-helper.ts`）：

1. 启动 5 秒后通过 GitHub Releases API 检查最新版本，semver 高于当前版本且存在 `toolbox-<version>-mac-<arch>.zip` 资产时自动下载；
2. HTTPS 流式下载 ZIP 并实时计算 SHA-512，与 `latest-mac.yml` 中的校验和比对；元数据缺失时降级为仅 HTTPS 完整性校验并在日志记录原因；
3. 用户点击“重启更新”或直接退出应用时，主进程以 `ELECTRON_RUN_AS_NODE=1` 启动随包安装的 `Resources/update-helper.js`（纯 Node 脚本），随后退出；
4. helper 等待主进程退出 → 校验 ZIP 条目无路径逃逸 → `ditto` 解压 → 校验应用 `CFBundleIdentifier`（`com.toolbox.app`）与版本 → 移除 quarantine → 原子替换（目标目录不可写如 `/Applications` 时经 `osascript` 弹管理员授权）→ 失败回滚 → 写入结果文件 → `open` 重启；
5. 下次启动读取结果文件：上次安装失败时在界面提示，成功后仅记录日志；`~/Library/Application Support/工具盒子/update/` 下的下载包、暂存与备份目录超过 7 天自动清理。

macOS 更新包替换前会清除 quarantine 属性，未签名应用不会再次被 Gatekeeper 拦截；但未签名应用首次启动仍可能被系统“无法验证开发者”提示拦截，正式分发前仍建议配置 Developer ID 签名/公证。

### Windows（electron-updater）

Windows 未配置 `publisherName`，electron-updater 不做发布者签名校验，未签名 NSIS 产物可正常更新；主进程 `electron/updater.ts` 在非 macOS 平台保留原有 electron-updater 链路。

### 测试提示

- 已发布版本（当前 latest 为 v0.1.1）无法再次收到更新，跨版本升级测试需发布更高版本（如 v0.1.2）；
- 本地冒烟测试：`node electron/update-helper.js --zip <zip> --target <app> --version <版本> --result <json> --wait-pid 0 --no-relaunch`。

## CI

`.github/workflows/desktop-release.yml` 在 `workflow_dispatch` 或 `v*` 标签触发，分别使用 `macos-14` 和 `windows-latest` 构建，并上传未签名的安装包及 SHA-256 校验文件。推送 `v*` 标签时，额外的 `publish` job 会下载两个平台的构建 artifact，整理更新元数据并创建 GitHub Release；手动运行 workflow 不会自动发布 Release。
