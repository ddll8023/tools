# 工具盒子 — 模块说明文档

> 本文档说明系统的业务功能设计、模块边界和协作关系。
> `doc/项目结构文档.md` 负责说明代码组织，本文档负责说明业务模块如何支撑产品能力。
> 更新日期：2026-06-23

---

## 1. 文档定位

本文档面向参与工具盒子项目的开发者和架构评审人员，从业务视角描述系统的功能模块划分、端侧职责以及模块间的协作关系。读者应首先阅读本文档理解整体设计意图，再结合源码进行开发。

## 2. 系统功能定位

工具盒子是一个**本地化的功能性工具集合桌面应用**，围绕以下核心能力方向设计：

| 能力方向 | 业务目标 |
|---|---|
| 工具插件化 | 每个工具作为独立插件接入，新增工具不修改核心代码 |
| 本地优先 | 所有文件处理在用户本地完成，不上传至任何服务器 |
| 统一操作入口 | 用户通过统一的桌面界面启动和使用所有工具 |
| 文档格式转换 | 首期聚焦 PDF 转 Markdown，后续扩展更多文档处理能力 |

## 3. 端侧职责划分

| 端侧 | 职责定位 | 设计关注点 |
|---|---|---|
| 前端界面 | 工具展示、用户操作入口、文件上传与结果预览 | 数据驱动的工具列表渲染、可收起侧边栏导航、单页面内完成操作流程 |
| 后端服务 | PDF 解析、Markdown 生成、文件临时存储 | 插件式工具注册机制、统一的响应格式、临时文件生命周期管理 |
| 桌面壳 | 应用窗口管理、后端子进程生命周期、系统集成 | 后端健康检查、窗口关闭时优雅退出、进程间通信 |

当前阶段：前端骨架、Electron 壳、后端骨架均已实现，三层架构可串联启动。

## 4. 功能模块总览

| 模块 | 定位 | 核心产出 |
|---|---|---|---|
| 布局框架 | 提供统一的桌面应用外壳 | 顶部栏、侧边栏、内容区的组合与路由分发 |
| 工具注册与路由（前端） | 集中管理工具清单，生成路由配置 | 工具配置数组、自动生成的路由、侧边栏和首页的数据源 |
| 首页工具网格 | 展示所有可用工具，作为用户的第一站入口 | 三列工具卡片网格、空状态提示 |
| PDF 转 Markdown | 首期核心工具，双引擎文档格式转换 | 标准模式（PyMuPDF 快速同步）、深度模式（MinerU 异步 AI 解析）、真实进度轮询 |
| 导航侧边栏 | 提供工具之间的快捷切换 | 可收起侧边栏、当前工具高亮、首页入口 |
| 全局状态管理 | 管理跨组件的 UI 状态 | 侧边栏展开/收起状态 |
| 后端服务注册 | 提供后端基础服务和工具注册接口 | `/api/v1/health` 健康检查、`/api/v1/tools/list` 工具列表、统一响应格式 |
| 后端异常处理 | 统一处理业务异常和未预期错误 | ServiceException 分层处理、全局异常处理器兜底 |

## 5. 各业务模块说明

### 5.1 布局框架

- **定位**：作为整个应用的骨架，承载所有页面的公共区域
- **核心功能**：
  - 固定高度的顶部栏，包含汉堡菜单、品牌名、当前工具名、搜索框（预留）
  - 侧边栏与内容区的左右分栏布局
  - 根据路由自动切换侧边栏默认状态（首页收起、工具页展开）
  - 错误兜底：未匹配路由时展示 404 页面
- **设计边界**：布局框架不感知具体工具的功能细节，只提供容器和导航能力
- **关联模块**：导航侧边栏、工具注册与路由、全局状态管理
- **开发关注点**：
  - 侧边栏默认状态应通过路由元数据声明，而非硬编码判断页面路径
  - 顶部栏搜索框当前为静态占位，后续接入搜索功能时注意不破坏布局结构
  - 布局组件命名遵循 App 前缀规范

### 5.2 工具注册与路由

- **定位**：工具清单的单一数据源，驱动侧边栏渲染和前端路由注册
- **核心功能**：
  - 定义 `ToolConfig` 接口，声明工具的 id、路径、名称、图标、组件等信息
  - 维护 `toolConfigs` 数组，集中管理所有已注册工具
  - 提供 `generateToolRoutes()` 函数，将工具配置自动转为 Vue Router 子路由
  - 首页和侧边栏都从此数据源读取工具列表
- **设计边界**：不包含任何 UI 渲染逻辑，只负责数据结构定义和路由生成
- **关联模块**：布局框架、首页工具网格、导航侧边栏、PDF 转 Markdown
- **开发关注点**：
  - 新增工具只需在 `toolConfigs` 数组中追加一条记录，零改动其他文件
  - `ToolConfig` 中的 `component` 使用动态导入，确保路由懒加载
  - 新增字段时同步更新 `types/tool.ts` 中的接口定义

### 5.3 首页工具网格

- **定位**：用户打开应用后首先看到的页面，展示全部可用工具
- **核心功能**：
  - 品牌 Logo 和产品标题展示
  - 三列自适应网格，每张卡片显示工具图标、名称和描述
  - 点击卡片跳转到对应工具页面
  - 无工具可用时显示空状态提示
- **设计边界**：首页只做展示和导航入口，不承担任何工具功能
- **关联模块**：工具注册与路由（作为数据来源）
- **开发关注点**：
  - 卡片数量较少（预计不超过 20 个），无需虚拟滚动优化
  - 首期只有一个工具时，使用 `justify-items-center` 保持卡片视觉居中

### 5.4 PDF 转 Markdown

- **定位**：首期核心业务工具，提供完整的文档格式转换体验
- **核心功能**：
  - 文件上传：支持拖拽和点击两种方式上传 PDF，限制 .pdf 格式和 50MB 大小
  - 双引擎转换：
    - 标准模式：PyMuPDF 同步解析，快速轻量，适合常规 PDF
    - 深度模式：MinerU 异步 AI 解析，适合复杂排版、扫描件、多栏布局
  - 转换进度：
    - 标准模式：CSS 脉冲动画（占位展示）
    - 深度模式：真实百分比进度条 + 阶段描述，通过 HTTP 轮询 `/progress` 端点获取
  - 结果预览：展示转换后的 Markdown 内容，含页数、表格数、图片数统计
  - 结果操作：下载 .md 文件、复制内容、重新上传
  - 异常处理：转换失败时展示错误原因和建议
- **设计边界**：后端已集成 PyMuPDF 标准引擎 + MinerU 深度引擎，前端通过 API 触发转换；深度模式为异步任务（`ProcessPoolExecutor`）+ 轮询真实进度
- **关联模块**：工具注册与路由（注册该工具的路由和导航信息）、布局框架、PDF 转 Markdown Schema（后端）、PDF 转 Markdown Service（后端）、PDF 转 Markdown Deep Service（后端）、PDF to Markdown Helpers（共享辅助函数）
- **开发关注点**：
  - 四种 UI 状态（上传/进度/结果/错误）覆盖完整交互流程
  - **双引擎架构**：标准模式（PyMuPDF 同步快速）、深度模式（MinerU 异步 + HTTP 轮询真实进度）
  - 深度模式在文件上传前勾选"深度解析"复选框，转换过程中展示真实百分比和阶段描述
  - 标准模式下 convert 为同步调用，前端进度为动画占位；深度模式下 convert 立即返回 task_id，前端每 1.5s 轮询 `/progress` 端点
  - 新增接口：`POST /api/v1/tools/pdf-to-markdown/progress` 查询深度解析进度
  - 深度模式使用 `ProcessPoolExecutor` 在独立进程中运行 MinerU CLI，避免阻塞事件循环
  - MinerU 模型从 ModelScope 下载，缓存在 `models/mineru/` 目录（项目内）
  - 后端返回的 markdown 中图片为相对路径，前端预览中不显示，下载后本地可正常查看

### 5.5 导航侧边栏

- **定位**：工具之间的快捷切换面板
- **核心功能**：
  - 展示所有已注册工具，支持单击切换
  - 当前所在工具高亮显示
  - 首页入口固定于侧边栏顶部
  - 侧边栏可完全收起/展开，由顶部栏汉堡按钮控制
  - 无工具可用时显示空状态提示
- **设计边界**：侧边栏完全隐藏而非图标模式，收起时内容区获得最大宽度
- **关联模块**：布局框架（作为子组件）、工具注册与路由（作为数据来源）、全局状态管理
- **开发关注点**：
  - 侧边栏条目应与首页工具卡片使用同一数据源确保一致性
  - 收起/展开动画使用 Tailwind transition 类实现，避免额外 CSS 动画定义

### 5.6 全局状态管理

- **定位**：管理跨组件的 UI 共享状态
- **核心功能**：
  - 侧边栏展开/收起状态的管理
  - 提供 toggle 和 set 方法供其他组件调用
  - 路由变化时自动根据 meta 信息重置侧边栏默认状态
- **设计边界**：当前仅管理侧边栏状态，后续可扩展其他全局 UI 状态（如主题偏好）
- **关联模块**：布局框架、导航侧边栏
- **开发关注点**：
  - 使用 Pinia Composition API 风格定义 Store
  - 新增全局状态时遵循按功能拆分为独立 Store 的原则

## 6. 通用支撑能力

### 6.1 图标体系

- **职责**：提供全应用统一的图标使用方案
- **使用原则**：所有图标通过 `<font-awesome-icon>` 组件使用，在 `main.ts` 中用 `library.add()` 统一注册后按需引用
- **开发时应避免**：不要在组件中直接使用 FontAwesome CDN 或 `<i>` 标签，避免在未注册的情况下引用图标

### 6.2 样式体系

- **职责**：基于 Tailwind v4 的 CSS-first 主题配置，提供品牌的颜色变量和原子化样式工具
- **使用原则**：优先使用 Tailwind 原子类，复用频率高的组合用 `@apply` 提取，自定义 CSS 仅作为后备方案
- **开发时应避免**：不要在多个文件中重复定义相同的颜色值或间距值，所有品牌色通过 `@theme` 统一声明

### 6.3 路由与导航

- **职责**：管理页面间跳转和工具路由的自动注册
- **使用原则**：所有路由组件使用动态导入实现懒加载，侧边栏和首页的导航数据源统一来自 `toolConfigs`
- **开发时应避免**：不要在侧边栏或首页硬编码工具列表，避免绕过路由直接操作 DOM 导航

## 8. 典型业务闭环

### 闭环 1：打开应用 → 浏览可用工具

1. 用户启动应用，布局框架加载，侧边栏默认收起
2. 首页从 `toolConfigs` 读取工具列表，渲染三列卡片网格
3. 用户浏览所有可用工具，了解每个工具的功能描述

### 闭环 2：使用 PDF 转 Markdown 工具（标准模式）

1. 用户在首页点击"PDF 转 Markdown"卡片，或通过侧边栏导航进入
2. 工具页加载，侧边栏自动展开并高亮当前工具
3. 用户拖拽或点击选择 PDF 文件
4. 文件上传后，页面展示脉冲动画进度，后端 PyMuPDF 同步解析
5. 转换完成，页面展示 Markdown 预览结果，包含页数、表格数、图片数等统计
6. 用户可下载 .md 文件或重新上传

### 闭环 3：使用 PDF 转 Markdown 工具（深度模式）

1. 用户在工具页勾选"深度解析"复选框
2. 拖拽或点击选择 PDF 文件
3. 页面展示真实百分比进度条 + 阶段描述（排队→初始化→加载模型→OCR→布局分析→提取→生成）
4. 后端启动 `ProcessPoolExecutor` 独立进程，调用 MinerU CLI 完成 AI 解析
5. 前端每 1.5s 轮询 `/progress` 端点获取进度
6. 进度达 100% 后自动获取预览结果，展示 Markdown 内容
7. 用户可下载 .md 文件或重新上传

### 闭环 4：多工具切换

1. 用户在某个工具页面内
2. 通过侧边栏点击其他工具（或返回首页）
3. 路由切换，内容区刷新为新工具页面
4. 侧边栏保持展开状态，新工具高亮

## 9. 后续开发参考原则

1. **新增工具时，只修改 `tools.ts` 的工具配置数组，不修改布局组件和路由文件**
2. **每个工具页是一个独立的功能模块，不依赖其他工具的业务逻辑**
3. **后端每个工具对应一个独立的 API 路由模块，通过扫描注册机制挂载**
4. **前后端工具列表应保持同步**：后端注册中心提供工具清单接口，前端启动时获取并与本地配置校对
5. **临时文件归工具管理**：每个工具的临时文件放在独立的子目录中，避免工具间文件命名冲突
6. **顶部栏搜索框为全局预留功能，当前应保持静态占位，不被单个工具占用**
7. **Electron 层不感知具体工具**，只负责启动后端进程、打开前端窗口、退出时清理子进程
8. **后端 health 接口是 Electron 与后端的唯一握手协议**，后端启动后必须尽快响应 `POST /api/v1/health` 返回 `{code: 0}`
9. **全局状态管理按功能拆分为独立 Store**，不将所有状态集中在一个 Store 中
10. **工具页的 UI 状态机（上传/进度/结果/错误）应作为通用模式，后续工具复用此模式**
11. **双引擎工具应提供用户选择开关**：同一工具提供"标准/深度"两套处理引擎时，用户应能主动选择，而非系统自动猜测
